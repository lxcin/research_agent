## 已确认的默认行为

**新一轮基线 = 本轮实际执行、第一次修改前的工作区文件 + 当时的暂存区状态。** 打开聊天窗口本身不固定基线。

上一轮完成后，人工修改是下一轮的有效输入。建立新基线时不与上一轮结束快照合并，不要求重新审阅，也不自动 Git 提交。三方合并只在用户主动撤销且出现后续修改时使用。

任务执行、任务恢复和文件撤销分别判断。结束快照不足可能让上一轮精确撤销不可用，但不必因此阻止整个会话继续。普通网络故障先自动重试、暂存和恢复；只有不能自行核实的副作用或实际冲突，才需要用户决策。

默认按单用户、共享工作区串行执行处理：A 完成后修改留在工作区，B 开始执行时从这些文件建立基线，撤销 B 保留 A 的结果及期间人工修改。独立 worktree 保留为显式可选能力，已有独立绑定保持其目录归属，不在后台静默迁回共享目录。

默认不把人工与 Agent 持续同时编辑作为主流程。保留现有工作区凭证和写入前校验即可；发现实际变化后重新读取相关文件并调整计划。多窗口同位置并发、细粒度资源调度和跨会话依赖不作为本阶段建设目标。

## 本阶段的最小闭环

1. 本轮实际执行取得工作区凭证，在第一次修改前保存内部快照 S，保留用户真实 index。
2. Agent 修改直接写入当前工作区；本轮相关写入结束后，保留结果，并按现有能力记录结束版本 E。
3. 用户正常继续时，以当前工作区创建下一轮 S，再退休旧引用；不依赖旧 E 是否完整。
4. 只有用户主动撤销时才比较版本，必要时使用已有三方合并。普通任务完成不新增自动 Git 提交或跨分支合并。

“修改后并入”在共享工作区中就是保留实际文件结果；不是先给每个窗口复制工作区再执行一次通用合并。内部快照使用临时 index / Git 对象，不自动把用户代码 git add 到真实暂存区。本轮回复已返回但后台仍写入时，工作区仍忙，下一轮须等待该写入停止。

先完成这个闭环和现有网络重试体验的改善。下文跨进程续跑、工具自动结果核对等作为后续分批事项，不与基线简化捆绑交付。

## 第一批：解除新轮与旧撤销证据的绑定

本批代码已实施，先验收再扩展恢复范围。

1. 接入时继续检查实际工作区凭证、后台写入及正在应用的撤销。旧执行仍持有写入权时等待/报告忙；不能因缺 E 就推断它仍在写入，也不能因锁已释放就推断所有外部进程都停止。
2. 没有残留写入或未完成应用时，直接从当前工作区创建新 S，包括人工新增、修改、删除以及暂存内容。
3. 新 S 成功发布后，退休上一轮 S/E、候选引用及旧消息；交给已有异步 Git 维护回收。新 S 创建失败则保留原现场及旧引用。
4. 旧轮缺 E、ready 消费失败等只影响该轮撤销可用性，记录具体原因；不补造 E，不要求用户为开始新一轮确认旧基线。
5. 未开始写入的撤销计划，包括 conflict，可在进入新轮时自动标为过期并使令牌失效；独立冲突产物中人工编辑的结果按现有文件登记保留，先不增加自动识别/删除人工产物的逻辑。applying / partial 继续走既有恢复流程。

本批复用现有快照和消息表，以 undo_unavailable 状态及 error 原因表达仅缺结束捕获证据；执行是否忙仍由独立的资源/任务状态判断。避免用一个 recovery_required 同时表达所有情况。过期冲突目录写入独立 retained 登记，后续换轮继续保留，需要人工清理；不尝试自动识别哪些文件已被人工编辑。

验收场景：上一轮成功 → 人工修改工作区及 index → 开始下一轮；上一轮缺 E 但没有残留写入 → 正常建立新基线；新基线失败 → 旧证据仍在；真实后台写入和 partial undo → 继续阻断；未应用冲突计划 → 过期，不阻断新轮；旧消息和旧令牌不能影响新轮。

## 第二批：网络中断与安全恢复

已实施范围和精确恢复语义见[网络中断与执行恢复](NETWORK_RECOVERY.md)。下表中的通用只读/幂等工具未知结果探测尚未落地；这类工具仍沿用已有 started 拒绝与显式核对入口。模型网络失败不会因此要求重新审阅已完成工具。

先交付进程仍存活的网络恢复，再覆盖宿主重启后的续跑。

| 中断点 | 默认恢复方式 | 是否重审 |
| --- | --- | --- |
| 模型请求未返回完整结果 | 沿用退避重试；持续失败时暂存上下文与执行位置，等待连接恢复 | 否 |
| 回复流已输出一部分 | 保留已输出内容并记录中断，从完整保存的步骤边界继续，不把半截工具参数当成调用 | 否 |
| 工具已有 completed 记录 | 恢复结果到上下文，跳过实际执行 | 否 |
| 只读工具结果未知 | 在工具契约允许时重试 | 否 |
| 幂等工具结果未知 | 使用同一幂等键查询或重试，记录核对证据 | 否 |
| 本地命令/容器执行中断 | 先确认仍在执行还是已经停止，再决定等待、读取结果或重新规划 | 不默认重审 |
| 不可逆操作结果未知且无法查询 | 暂停相关操作，给出已知证据和具体选择 | 需要用户决策 |

暂存复用 executions.db 的执行位置、上下文、调用标识/结果与预算记录，并保留原授权的作用域。恢复不得重置预算、重复执行已完成工具或把原授权扩大到新参数/新资源。参数、目标和安全条件没有变化时不重复询问；确实改变时按对应操作契约重新授权。撤销计划的内容令牌仍绑定精确计划，目标变化则失效。

先在默认循环支持已持久化步骤边界的恢复。替代内核按其已有上下文/状态恢复能力接入，不保存任意 Python 调用栈，不把一种循环的内部游标强加给所有内核。

自动恢复同一任务时：工作区未变则从已确认步骤继续；文件已变化则重新读取受影响内容、保留已完成结果，再规划后续写入。必要时建立新的执行段基线，不能用旧快照覆盖当前文件。新用户输入到达后，先协调旧任务的暂停/取消与资源释放，不能让旧任务恢复后与新任务同时写入。

验收场景：断网与恢复、429/5xx、进程重启、已完成调用不重复、幂等调用不产生重复副作用、流式中断、人工改文件后恢复、恢复期间新输入、预算与授权范围保持。

## 第三批：收敛消息、阻断范围与交互

本批以现有状态与提示的收敛为主；跨会话细粒度隔离与依赖调度留待真实需求出现后再设计。

- outbox 继续负责事实记录、固定结束证据和重复消费；自动补 E 是撤销能力增强，不是每次接入的必经成功条件。
- 快照证据不足时停止该轮精确撤销；仍在写入时停止冲突工作区的新写入；单个远程操作结果未知时暂停该操作及其依赖步骤，不直接隔离所有无关会话。
- 在证据足够时自动核对、恢复或退休旧记录。存在隔离标记时按具体原因和核对结果处理，不直接删除标记绕过保护。
- 短暂重试不弹确认；长等待显示“已暂存，等待恢复”；旧撤销不可用可显示一次状态说明；只有明确需要用户选择的情况弹交互。
- 正常路径只维护最近一轮撤销数据。已有部分撤销/未停止执行所需的恢复证据继续保留；本批不引入新的历史快照归档系统。

## 模块责任

内核继续负责思考循环；runtime 协调步骤和上下文；执行器/工具声明执行、幂等与结果核对能力；资源服务确认写入者是否停止；checkpoint 管理本轮文件基线和撤销证据；outbox 发布和消费事实。复用现有 OS 凭证、执行日志及 SQLite 消息，不新增跨会话文件写入总线。

## 验收与实施顺序

第一批通过后再实施第二批；第三批随恢复行为收敛交互与文档。每批先做临时真实仓库、进程/网络故障注入的针对性验证，再运行相关回归；涉及后台凭证和容器生命周期时补跑真实 Docker 验收。

核心验收标准：

- 人工改后开始新轮，不出现合并或重审，基线等于当前文件与 index。
- 两个共享目录的窗口串行使用：A 完成 → 人工修改 → B 实际开始时保存基线 → 撤销 B，A 与人工已有内容保留；窗口提前打开不影响取基线时机。
- 单纯网络故障不会要求用户确认“是否已经执行”，也不会自动回滚已完成的代码。
- 缺旧 E 不阻止安全的新轮，存在残留写入或 partial undo 则仍有保护。
- 恢复不重复副作用，不扩大授权，不重置预算，不覆盖人工文件。
- 只有真实不可判定的副作用、不能安全处理的冲突才请求人工决策。
