# REFLECTION —— PaperPilot 项目反思

> 中文反思，批判性审视 Superpowers 方法论、AI 协作模式与整个 V1→V3 开发过程。

---

## 一、哪些 Superpowers 技能最有用？哪些是"形式大于实质"？

**`brainstorming` 和 `writing-plans` 发挥了最大作用。** 不是因为它们产出的文档本身，而是因为它们让我在动手之前就看到 AI 会做什么。通过 AI 对抗和 code-review 来验证项目在预想轨道上运行——这种"先看剧本再演戏"的节奏，比直接让 AI 编码然后修修补补高效得多。

**`finishing-a-branch` 用处不大。** 我的开发模式是边做边修正想法——不是先定义好一个模块，做完封存，再做下一个。更像是顺着需求流往下走：做了 Agent Loop → 发现工具需要重构 → 重构工具 → 发现前端渲染不对 → 改前端。整个过程是连续的，很难切割成独立 branch。但这不意味着 git 管理不重要——commit 频次和信息仍然关键。

**`test-driven-development` 是有意义的约束。** 不论如何，能增加我对项目掌控力的就是正向的。我得知道 AI 做了什么——测试就是这种"知道"的载体。也许把测试也用 brainstorming 这套方法思考一遍，对我会更有意义：先想清楚要测什么边界条件，再让 AI 写代码。

---

## 二、TDD 在 AI 协作下是阻碍还是放大器？

**先写测试。如果重来，应该也是测试更好。**

测试能很快检查出代码的基础错误。V3 重构时，`test_filesystem_tools.py` 的 19 个测试在一开始就帮我验证了文件读写的核心逻辑没有因为 workspace 模型改变而崩坏。`test_hitl.py` 和 `test_feedback_loop.py` 则让我确信 guardrail 和 auto_validate 不是"写在提示词里的安全"。

但 TDD 有一个前置条件：你得先想清楚要什么。如果连想要的界面是什么、按钮点击发生什么都不知道，测试无从写起。这引出了后面要说的——开头那一步的"想清楚"才是最大的瓶颈。

---

## 三、Subagent 能自主运行多久不脱轨？

**给出详细要求后其实很少偏离。**

V3 重构时的重写工具系统逻辑、SSE 协议改造、前端组件重建——这些 subagent 都在一次对话内完成，产出的代码质量可用，不需要大量人工修正。

偏离的情况出现在**要求本身模糊**的时候。比如前端界面：因为前端没办法通过测试来确认准确性，得人工去看，然后又要说明"我要哪些按钮、点了之后发生什么"。调了一会是正常的——主要是我自己一开始没把想要的界面效果说清楚。

---

## 四、什么粒度的 Task 最优？

**一个模块。** 模块内部有良好内聚性，对人来说也只需要知道这个模块是什么、有什么方法、能做什么。

比如 `project_manager.py`（17 个函数，约 280 行）就是一个好的 task 粒度。它的边界清晰：输入是 workspace_dir，输出是 JSON 文件和 chats 列表。Subagent 不需要理解 Agent Loop 或前端渲染，只需要保证数据读写的正确性。

太细了（比如"写一个函数"）浪费 subagent 的上下文窗口。太粗了（比如"重写整个后端"）会让 subagent 在设计决策层面出错——它没有全局视野。

---

## 五、SPEC 不清导致 Subagent 偏离的具体案例

**前端界面调整。**

原因很直接：前端没办法通过测试来确认准确性。测试可以检查组件是否渲染、函数是否返回正确值，但无法判断"这个按钮放在这里好不好看""这个折叠展开的动画自然吗"。所以我得人工去看，然后告诉 subagent"这边加一个删除按钮""标题太长了截断到第一句话"。

说到底是**我一开始没把想要什么效果和按钮说清楚**。如果重来，我会先画一个完整的界面草图——每个组件的位置、点击后发生什么、折叠展开的交互细节——然后再让 subagent 实现。这样就不需要在实现后反复沟通"这边不对"。

---

## 六、最有效的 Prompt/Context 策略

**工具描述是最关键的迭代点。**

V3 经历过一次工具描述的重写。最早的意图路由（关键词匹配意图 → 削减工具列表）试图减少 LLM 的混乱，但反而因为意图分错导致 LLM 拿不到需要的工具。后来**删除了意图路由**，所有人 13 个工具全量暴露，把精力放在优化每个工具的描述上——特别是互斥工具的区分（"retrieve 只搜本地，search_papers 只搜 arXiv"）。

另一个关键迭代是**回复格式的描述**。从"思考后行动"到"直接做事，不要道歉，不要在回复里说'我可以帮你'"——这是从 LLM 回答的"聊天模式"切换到"执行模式"。系统提示里写了**不做什么**（不道歉、不自述、不重复文件内容）比写**做什么**更有效。

---

## 七、凭据与分发需求迫使你思考了什么？

**安全和可用性。**

API Key 的流经路径（前端 localStorage → POST body → 后端内存 → litellm 参数）如果不逐段梳理，很容易在某一段泄露。Docker 分发让我意识到容器内的 config.yml 路径和宿主机不同——这些"别人怎么跑起来"的问题，是自己在本地开发永远不会考虑的。

CI 中加了凭据扫描（`grep -rPn "sk-[a-zA-Z0-9]{20,}"`），虽然简单但比没有好得多。这让我意识到安全不是"设计一个完美的加密方案"，而是"在每个可能泄露的口子上放一个哨兵"。

---

## 八、如果重来，会改变什么？

**会先想好一个完整使用的界面。**

不是技术架构——架构 V1→V2→V3 迭代是正常的。而是**用户故事和使用描述的细节**：点击这个按钮会发生什么、对话列表怎么排序、工具调用结果折叠还是展开、文件变更怎么展示 diff。这些"界面需求"是 subagent 最容易偏离的地方，因为没办法用测试验证。

如果有清晰的界面规范在前，前端重构不会花那么多轮沟通。技术架构反而可以慢慢迭代——但用户看到的第一眼，应该是确定的。

---

## 九、对 Superpowers 方法论的批判

**它的核心假设——"通过 TDD 和计划可以一次生成合适的产品"——在我的项目里不成立。**

但这不是 Superpowers 的错。是我自己没想好一开始要什么。

经历了 V1→V2→V3 三个大版本，我认为**迭代是比计划更重要的一环**。轻量化的计划 + 最小可行版本的开始 + 人工使用和修正，比形式化的流程更有价值。不是不要计划——需要——但不要指望计划能覆盖所有细节。

TDD 和严格的 task 分割在"你知道你要什么"时是加速器，在"你还在探索要什么"时是枷锁。这个项目的大部分时间花在后者——探索 governance 应该多深、SSE 协议应该多结构化、前端渲染应该多干净。这些问题没法在第一天写进 SPEC。

所以我的结论是：**Superpowers 是一个好的"执行框架"，但不是一个"探索框架"**。当目标清晰时它帮你跑得快；当目标模糊时你需要先自己跑一遍再回来写 SPEC。

---

## 核心洞察

这个项目最重要的贡献不是检索算法或前端 UI——是 **Governance**。

V3 的三层纵深——guardrail（12 个危险模式正则）+ HITL（threading.Event 审批状态机）+ auto_validate（文件写入后 py_compile/pytest 回灌）——全部是确定性代码。没有一行依赖 LLM 的 prompt。

这揭示了一个根本洞见：**当 LLM 负责思考，工程价值在 harness。** LLM 会越来越聪明，但聪明和可靠是两回事。Harness 的职责不是让 Agent 更聪明，而是确保聪明的 Agent 不会做蠢事——guardrail 设"绝不能"的硬边界，HITL 设"你可以做但要我确认"的审批带，auto_validate 设"你做完了我帮你检查"的反馈闭环。

最终，Harness 是马鞍和缰绳，LLM 是马达。马鞍越紧、马达越安全；缰绳越短、方向越可控。但只有缰绳没有马达，也到不了目的地。
