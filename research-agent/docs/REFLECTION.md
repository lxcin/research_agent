# REFLECTION —— PaperPilot 项目反思

> 中文反思，基于 V1→V2→V3 实际开发过程，审视 Superpowers 方法论与 AI 协作的适用边界。

---

## 一、哪些 Superpowers 技能有用？哪些是形式？

`brainstorming` 和 `writing-plans` 有用，但用处不在文档本身——在于逼我在动手前说清楚"到底要做什么"。和 AI 来回讨论需求的半小时，比拿到一份漂亮 spec 然后开始编码更值钱。AI 追问"这个场景的退化路径是什么""用户点了取消之后怎么办"时，我被迫想清楚原本没想的问题。

`finishing-a-branch` 在我的开发节奏里基本没用到。原因是我的开发不是"定义模块→做完→封存→下一个"的瀑布流。实际过程是：做了 Agent Loop，发现工具调用拼到前端消息里一团乱，回头改 SSE 协议，改完发现前端需要组件化渲染，又去重构 ChatArea。整个过程连续，切不出独立 branch。每个 commit 是有意义的，但 branch 的隔离边界不存在。

`test-driven-development` 的约束本身有意义。不管过程怎么乱，每次让 AI 干完活后跑测试，至少能确认基础逻辑没崩。`test_filesystem_tools.py` 的 19 个测试在 V3 workspace 模型重构时帮了大忙——跑一遍就知道 `_get_project_dir` 和 `_safe_path` 的行为没有因为改 workspace 路径而退化。

---

## 二、TDD 在 AI 协作下是阻碍还是加速？

我试过两种顺序。V1 是先写实现再补测试——结果测试写得像是给实现"找理由"，很多边界条件没覆盖。V3 是写完 spec 后先写测试，再让 AI 写代码——`test_hitl.py` 和 `test_feedback_loop.py` 就是这种顺序。测试先定义好"guardrail 应该在什么输入下返回什么"，然后 AI 填代码，跑测试，红了就修。

但 TDD 有一个前提：你得先知道要测什么。如果连想要的界面效果都说不清——按钮放哪、点了弹出什么、文件变更怎么展示 diff——那测试写不了。前端这块我一直到最后都是人工看、手工调，因为没法给 UI 交互写断言。

---

## 三、Subagent 偏离主题的频率？

给具体指令时很少偏离。V3 的 `project_manager.py` 有 17 个函数、明确的输入输出签名，subagent 一次写完，跑测试不红，代码可用。

偏离的情况出现在指令模糊的时候。前端改了好几次——不是因为 AI 乱写，是因为我自己没说清。"加一个对话框删除按钮"——AI 加了按钮但没加二次确认弹窗。"标题用用户的简短句子"——AI 用了截取前 30 字，但中文句子边界不是按字符数切的，应该是"截到第一个标点"。这些都是我用了几次之后才"发现"的需求，不在最初的 spec 里。

---

## 四、Task 多大合适？

差不多 `project_manager.py` 这个量级——一个模块、十几个函数、两百多行。有内聚性，输入输出清楚，不需要理解全局。

太细了浪费上下文。太粗了 AI 在设计决策上容易出错——比如"重写整个 agent 循环"这种 task，AI 可能会选一个能跑但不是最合理的设计，因为它没有试过上一版哪里卡住了。

---

## 五、SPEC 不清导致偏离的案例

T9 项目路由。SPEC 写了"关键词重叠匹配"六个字。Subagent 实现了英文空格分词的 TF-IDF 匹配，单元测试全绿。但实际用户输入"上次那个 Transformer 的 attention 机制分析结果怎么样了"——全中文、全被当成一个 token，匹配分数永远 0。

修了两步：引入 jieba 中文分词，然后把阈值从 0.5 降到 0.15。"关键词重叠匹配"这六个字的模糊性，在 subagent 手里变成了"英文空格分词的 TF-IDF"——这是合理的英文默认，但对中文场景完全不够。如果 spec 里写了"必须处理中文输入"，subagent 会直接上 jieba。

从这之后我给 AI 的 spec 都加上了"不能做的假设"——"不要假设输入是英文""不要假设工作区目录一定存在"——比"要做什么"更防偏离。

## 六、Prompt 策略中哪些改动有效果？

尝试过三种方案：

第一个是给系统提示加意图路由——关键词匹配后只给 LLM 看部分工具。效果差。"完成这道题目"被分到"default"意图，file_write/file_glob 全被过滤，LLM 想写文件写不了。删掉了。

第二个是调整工具描述。LLM 最常混淆的是 `retrieve`（搜本地）和 `search_papers`（搜 arXiv）。原因是它不知道 arXiv 搜索结果没进本地库。给每个容易混淆的工具描述加了一句反例——"search_papers 返回的论文不在本地，不能用 retrieve 找"——问题基本解决。

第三个是改回复格式的系统提示。从"思考后行动，诚实说明能力边界"改成"直接给出结果。不要在回复里说'我可以帮你'。不要道歉。不要重复文件内容。"效果明显——LLM 不再用一整段话自述它刚才做了什么，回复变短了、信息密度高了。

还有一个小技巧：把关键约束放在 context 的末尾。LLM 对最后一条 system message 的注意力明显高于中间。工具描述的反混淆句子、回复格式规则，我都塞在最末尾。

## 七、凭据与分发让你多想了什么？

API key 的前端 localStorage → POST body → 后端内存 → litellm 参数，四个节点如果不逐段检查，很容易在某个节点留下明文。实际做法很简单：前端不持久化 key（点保存才写 localStorage），后端收到后只放内存不写日志，传给 litellm 时用 `api_key=` 参数而非环境变量。

Docker 让我意识到路径问题——容器内 `~/research-agent-data/` 和开发机不同，config.yml 位置的写死会让容器启动失败。修成了 `get_data_dir()` 动态读环境变量 `RESEARCH_AGENT_DATA_DIR`。

CI 里加了凭据扫描 `grep -rPn "sk-[a-zA-Z0-9]{20,}" src/`，虽然只是字符串匹配，但至少挡住了手滑提交明文 key。

## 八、如果重来，会怎么开始？

先画界面草图，再写技术架构。不是因为界面比架构重要，而是界面的交互细节——"对话列表怎么排序""工具调用结果是折叠还是展开""文件变更显示 diff 还是全量""删除对话要不要二次确认"——这些是 subagent 最容易偏离的地方，也是自动化测试覆盖不到的。

架构反而是可以迭代的。Agent loop 从 LangGraph 改成自研 while 循环再改成 litellm function calling，改了三次也没太大问题——因为接口清晰、测试挡着。界面改了三次，每次都要人工重看一遍所有交互。错的成本不一样。

## 九、Superpowers 方法论在你的项目里适用吗？

Superpowers 的默认流程是 brainstorm → plan → branch → subagent → tdd → review → finish。这套流程假设**你能在第一天定义清楚要什么**。

V1 我基本按这套走，出了一些能跑的代码，但 V3 回头看至少有四个重要决策是 V1 的 spec 完全没覆盖的：要不要自己做 Agent Loop（V1 用了 LangGraph 框架）、文件系统还是 SQLite 存项目数据（V1 选的 SQLite）、SSE 事件要不要结构化（V1 是裸文本拼 HTML 标签）、guardrail 要不要接 HITL（V1 guardrail 只定义没调用）。

这些不是 spec 写得不好——是我当时根本不知道这些是问题。你在看到 AI 把工具调用日志和最终回复混在一段 HTML 里之前，不会觉得"SSE 需要结构化"是个需求。这个"发现需求"的过程，靠 brainstorming 替不了，只能靠实际跑起来、人工试一遍。

所以这九周的节奏是：跑一遍 → 发现哪里不舒服 → 回去改。不是"按 spec 一次生成"。

迭代本身比计划重要。轻量 spec（知道要做什么但不过度设计）+ 跑一个 MVP + 人工用一遍发现问题 + 回去改——这套比严格执行 Superpowers 的全流程更贴合我实际的工作节奏。
